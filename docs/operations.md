# Эксплуатация

Документ для тех, кто разворачивает и поддерживает Ватсапку: переменные окружения, запуск, здоровье сервисов, журналы, резервные копии и обновление.

## 1. Состав стека

| Сервис | Роль | Порт на хосте |
|---|---|---|
| `frontend` | статика и прокси `/api`, `/ws` | `127.0.0.1:4200` (локально) |
| `backend` | REST и STOMP | `127.0.0.1:8080` (локально) |
| `worker` | задания, outbox, медиа, очистка | не публикуется |
| `migrate` | миграции Flyway; завершается после применения | не публикуется |
| `postgres` | PostgreSQL 17 | не публикуется |
| `redis` | Redis 8 | не публикуется |
| `minio`, `minio-init` | объекты и создание bucket при первом запуске | не публикуется |
| `mailpit` | локальный SMTP для проверки писем (профиль `mail`) | не доступен с хоста, см. раздел 8 |

Сети: `private` — внутренняя, без выхода наружу; в ней работают PostgreSQL, Redis, MinIO и миграции. `edge` — обычная; в ней backend, worker и frontend, которым нужен выход к Google и SMTP.

Служебный порт управления (`MANAGEMENT_PORT`, по умолчанию `9090`) слушает только loopback внутри контейнера. Наружу он не публикуется.

## 2. Переменные окружения

Секреты задаются в `.env` (локально) или в переменных окружения платформы. Шаблон — `.env.example`. В репозитории нет реальных значений.

| Переменная | Назначение |
|---|---|
| `POSTGRES_PASSWORD`, `DB_MIGRATION_PASSWORD`, `DB_PASSWORD` | пароли администратора кластера, роли миграций и роли приложения. Роли создаются при первом запуске базы |
| `JWT_SECRET` | подпись access-токенов (HS256). Не короче 32 байт; у каждой среды свой |
| `REDIS_PASSWORD` | пароль Redis |
| `MINIO_ROOT_USER`, `MINIO_ROOT_PASSWORD` | корневая учётная запись MinIO; нужна только серверу и инициализации bucket |
| `MINIO_ACCESS_KEY`, `MINIO_SECRET_KEY` | ключ приложения; не должен совпадать с корневым пользователем |
| `MINIO_BUCKET`, `MINIO_REGION` | bucket для медиа и регион |
| `APP_URL` | публичный адрес приложения, например `https://example.org` |
| `ALLOWED_ORIGINS` | разрешённые Origin для CORS, cookie-операций и WebSocket. Должен совпадать с адресом страницы |
| `REFRESH_COOKIE_SECURE` | `true` за HTTPS. `false` нужен только для входа по HTTP в локальной сети |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI` | OAuth-клиент Google. Адрес перенаправления: `<APP_URL>/api/v1/auth/google/callback`. Без клиента вход через Google не показывается |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_STARTTLS` | отправка писем: подтверждение почты и восстановление пароля |
| `MAIL_FROM` | адрес отправителя, например `Ватсапка <no-reply@example.org>` |
| `BOOTSTRAP_ADMIN_EMAIL`, `BOOTSTRAP_ADMIN_USERNAME`, `BOOTSTRAP_ADMIN_PASSWORD` | первый администратор. Создаётся при первом запуске, если его ещё нет. **После первого запуска переменные нужно очистить** |
| `JOB_CONCURRENCY`, `OUTBOX_BATCH_SIZE` | параметры worker |

Без `SMTP_HOST` письма не отправляются.

## 3. Запуск

```sh
cp .env.example .env          # заменить все значения
docker compose up -d --build
```

Порядок старта: `postgres`, `redis`, `minio` → `migrate` (применяет миграции и завершается) → `minio-init` → `backend` и `worker`. `frontend` ждёт `backend`.

Остановка (`docker compose down`) не удаляет volumes. Удаление данных — только `docker compose down -v` и только осознанно.

### Демонстрационные данные

Включаются явно: профиль `demo`, `DEMO_ENABLED=true`, `DEMO_PASSWORD` не короче 10 символов. Отказываются работать в профиле `production` и в процессе worker. Для production не включайте.

## 4. Миграции

- Миграции лежат в `backend/src/main/resources/db/migration` и применяются сервисом `migrate`.
- Применённую миграцию нельзя менять: Flyway сверяет контрольные суммы и не даст стартовать backend при расхождении. Исправления — новыми миграциями.
- Приложение работает с схемой в режиме `validate` и сама схему не меняет.

## 5. Здоровье и журналы

Backend и worker отвечают на служебном порту (внутри контейнера):

- `GET /actuator/health/liveness` — процесс жив;
- `GET /actuator/health/readiness` — готов принимать работу. Недоступная база даёт `503`. Redis и MinIO не входят в readiness: их сбой отображается статусом `DEGRADED`, но не останавливает сервис.

Healthcheck в compose использует readiness.

Журналы пишутся в stdout в формате ECS JSON с полем `service.name`; `traceId` есть у строк, относящихся к HTTP-запросу или заданию. Ротация `json-file`: 10 МБ на файл, три файла на контейнер.

Метрики доступны на служебном порту: `http.server.requests`, `whatsappka.ws.connections.active`, `whatsappka.jobs.queued`, `whatsappka.jobs.running`, `whatsappka.jobs.failed`, `whatsappka.jobs.oldest.queued.seconds`, пул соединений `hikaricp.*`, память JVM `jvm.*`. Экспорт в систему мониторинга в репозитории не настроен.

## 6. Резервные копии

Скрипты лежат в `infra/backup/`.

```sh
sh infra/backup/backup.sh                                  # копия в backups/<время UTC>/
sh infra/backup/restore.sh <каталог копии>                 # только в пустые volumes
sh infra/backup/restore.sh --replace-existing-data <каталог>  # заменяет данные
```

Что делает копия:

1. Останавливает записи: `backend` и `worker`. PostgreSQL и MinIO продолжают работать.
2. Снимает дамп PostgreSQL и архив объектов MinIO.
3. Записывает манифест с версией схемы и контрольные суммы.
4. Запускает `backend` и `worker` обратно, даже если копия не удалась.

В копию не входят Redis (кэш и краткоживущее состояние), `.env` и конфигурация платформы. Их храните отдельно и защищённо. Копии содержат персональные данные: храните их только в защищённом месте.

Восстановление проверяет контрольные суммы и совместимость схемы: копия не может быть новее миграций версии кода, которую вы запускаете. Если в volumes есть данные, восстановление ничего не меняет, пока не указан `--replace-existing-data`.

**План хранения** из требований: 7 ежедневных и 2 еженедельные копии. Скрипты старые копии не удаляют; удаление выполняется вручную.

**Внешняя копия.** Требуется хранить хотя бы одну копию вне сервера, на котором работает стенд. Внешнее место на данный момент не настроено.

Время остановки записей зависит от объёма данных. Перед первым расписанием замерьте его на реальных данных.

## 7. Обновление

1. Сделайте копию: `sh infra/backup/backup.sh`.
2. Сохраните предыдущие образы, чтобы можно было откатиться:

   ```sh
   docker image tag whatsappka-backend:local whatsappka-backend:previous
   docker image tag whatsappka-frontend:local whatsappka-frontend:previous
   ```

3. Обновите код и пересоберите стек: `docker compose up -d --build`.
4. Проверьте лог `migrate`: миграции применились без ошибок. Дождитесь `healthy` у backend.

### Откат

Откат на предыдущий образ безопасен, только если схема базы совместима со старым кодом. Миграции обновления уже применены — откатить образ нельзя. В этом случае восстановите копию, сделанную **до** обновления, и поднимите предыдущие образы. Копия, сделанная после обновления, для отката на старый код не подходит.

## 8. Ограничения и известные особенности

- Публикация портов на `127.0.0.1` для сервисов во внутренней сети (PostgreSQL, Redis, MinIO, mailpit) не работает: Docker не публикует порты контейнеров, подключённых только к внутренней сети. Для отладки используйте `docker compose exec`.
- Автоматических тестов в репозитории пока нет.
- Внешняя копия резервных данных не настроена.
- Шаблон переменных для внешнего адреса и override для compose лежат в `infra/coolify/`. Конфигурация проверена командой `docker compose config`; запуск через Coolify не проверен.
